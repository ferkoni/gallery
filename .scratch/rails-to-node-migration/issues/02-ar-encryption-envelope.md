# What is ActiveRecord Encryption's on-disk format, and can Node read it?

Type: research
Status: resolved
Blocked by: —

## Question

`S3Credential` declares `encrypts :access_key_id` and `encrypts :secret_access_key`
(`gallery-api/app/models/s3_credential.rb`), with no `deterministic: true`. Both columns
are `text` in the schema and hold an ActiveRecord Encryption payload, not raw ciphertext.

Establish the facts a Node reader would need:

1. What exactly does Rails 8.1 write into an `encrypts` column? The envelope structure,
   how headers/metadata are encoded, the cipher and mode, the IV and auth-tag placement.
2. How is the data key derived from `ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY` and
   `..._KEY_DERIVATION_SALT`? Which KDF and parameters?
3. What does non-deterministic mode change versus deterministic, and does it matter here?
4. Does any published Node/TypeScript library read this format? If not, how much code
   would a faithful reader be?
5. Is there a documented or officially sanctioned way to decrypt outside Rails at all, or
   is the format explicitly an internal detail?

Answer with citations to Rails source or official docs, not blog inference. The point is
to establish whether reading the format from Node is a real option or whether ticket 03
must migrate the data instead.

## Answer

**Yes, Node can read and write the format faithfully — proven round-trip, not inferred.**
Full findings, cited to `activerecord-8.1.3` as resolved by this project's gemset:
[`../research/02-ar-encryption-envelope.md`](../research/02-ar-encryption-envelope.md).

The facts ticket 03 needs:

1. **Envelope.** Plain UTF-8 JSON in the column, *no* outer base64:
   `{"p":"<b64 ciphertext>","h":{"iv":"<b64 12B>","at":"<b64 16B>"}}`. AES-256-GCM. The IV
   and auth tag are separate headers, never concatenated onto the ciphertext. Optional
   `"c":true` (a JSON boolean, not base64) means the plaintext was zlib-deflated *before*
   encryption, which Rails does when it exceeds 140 bytes. Optional `"e"` carries a
   non-UTF-8 encoding.
2. **Key derivation.** A single `PBKDF2-HMAC-SHA256(PRIMARY_KEY, KEY_DERIVATION_SALT,
   65536, 32)`, used directly as the AES key. No per-record data key and no envelope
   wrapping — that shape only appears under `EnvelopeEncryptionKeyProvider`, which this app
   does not use. `ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY` is uninvolved here, since
   neither column is declared `deterministic:`.
3. **Non-deterministic vs deterministic** differs only in IV generation (`cipher.random_iv`
   versus the first 12 bytes of `HMAC-SHA256(key, plaintext)`). Irrelevant to a reader, and
   helpful to a writer: Node's output need only *decrypt* under Rails, not be byte-identical,
   so there is no JSON-key-ordering or compression-parity trap.
4. **No npm package implements this** — the registry has nothing. A working reader+writer
   was ~30 lines of `node:crypto` + `node:zlib`; production-grade with strict base64
   validation, the encoding map, key rotation and typed errors is ~150-250 lines.
5. **Not an external contract.** The guides describe the JSON shape but never state the KDF
   parameters; the Ruby source is the only source of truth. The `Encryptor#encrypt` doc
   comment is itself factually wrong — it claims a `SafeMarshal` serializer that does not
   exist and an outer Base64 step that does not happen.

**The caveat that matters: the risk is the key-derivation defaults, not the parser.** The
wire format is unchanged from Rails 7.0 to 8.1 (verified by diffing the two gems on disk),
but the PBKDF2 digest silently flipped SHA-1 → SHA-256 in `load_defaults "7.1"`. That is
*configuration*, not recorded in the envelope — nothing in the stored bytes tells a reader
which digest produced the key, so Node must hardcode an assumption it cannot verify from the
data.

**Bearing on ticket 03:** the format is not the reason to migrate. Node reading it is about
a day's work. The reason to prefer a neutral scheme is maintenance coupling — pinning a Node
module to undocumented Rails internals for two columns of AWS credentials. Whichever shape
03 picks, the research recommends read-old/write-new with Ruby still able to decrypt, never
a destructive in-place rewrite, plus golden vectors generated by the real app pinned into CI
so a Rails upgrade fails loudly rather than as an auth-tag error indistinguishable from
corruption.
